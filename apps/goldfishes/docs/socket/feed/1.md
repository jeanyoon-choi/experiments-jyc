# socket feed/1

- Date: 2026-10-27
- Relay: `socket/experiments/feed/1/` (`protocol.mjs`, `index.mjs`, `protocol.test.mjs`)
- Browser: `components/transport/feed/1/`; the phone slots are `slots.mjs` (+ `slots.test.mjs`)
- Speakers: [`/screen/bubble/7`](../../screen/bubble/7.md#연결-main-screen-of-socket-feed1) (screen) → [`/pc/mobiles/1`](../../pc/mobiles/1.md) (pc)

The main screen keeps a fixed set of phone slots, each following one goldfish, and sends what changed. The relay forwards it to every pc at once (NOTES 1023: one goldfish, one mobile).

## Who does what

| | |
|---|---|
| screen | sees the fish; steps the slots (`slots.mjs`) every 33 ms; sends only changes |
| relay | checks the form and forwards; no state, no timers |
| pc | follows one screen; draws |

Every timing lives in the browser (`slots.mjs` `TUNING`, `link/feed.ts`, the pc's CSS), so tuning is a reload, never a relay restart. This used to be otherwise: the relay kept the slots and their clock, and every tuning needed a restart (user, 2026-10-27: "제발 그럴 필요 없게"). The screen is the right owner because the fish live there. It knows at once when one reaches a bubble, lets go or dies, so it needs no keepalives or timeouts, and every pc sees the same assignment.

## Events

| Event | Direction | Payload |
|---|---|---|
| `join` | client → relay, ack | `{role, version: "1"}` → `{ok, error?}`; a wrong version or role is refused |
| `presence` | relay → room | `{screens, pcs, total, …}` |
| `push:in` | screen → relay | `{items: [{id, slot, fish, page, keyword, rank, seed, at}], released: [slot], idle: [slot]}` |
| `push:out` | relay → pcs | the same, with `screen` (its connection id) |
| `snapshot:in` | screen → relay | `{vocabulary: [{id, label, set}], slots: [{slot, fish, attached, history}]}`, on join and when asked |
| `snapshot:out` | relay → pcs | the same, with `screen` |
| `snapshot:request` | relay → screens | a pc has joined |
| `screen:gone` | relay → pcs | `{screen}`: its phones go dark |

## Slots (screen, `slots.mjs`)

- 64 slots, fed by the whole school: a fish feeds the slot its serial hashes to, so 380 fish give about 6 per slot, and no slot waits on one fish or goes dark (user, 2026-10-27). An earlier pass gave each slot one fish and darkened it whenever that fish let go; it read as "dead or alive, neither".
- Each touch is queued on its slot (up to 4). A slot puts out its next item once the last has shown for 0.15 s (`dwellMs`), so a burst arrives as a rapid run.
- The screen sends a contact whenever a fish reaches a bubble other than the one it was last at, even with the same keyword (user, 2026-10-27). `detached` and `departures` are still sent and ignored by the slots; `released` and `idle` are always empty.
- Each item carries a 32-bit `seed`. The pc chooses its content from it.

## Keywords are not part of the protocol

- A keyword is an id (`[a-z0-9][a-z0-9._-]*`, ≤ 64). The relay checks its form only.
- The screen owns the vocabulary (bubble/7: `link/feed.ts` `VOCABULARY`) and sends it with every snapshot.
- A pc looks up content by id. For an id it has nothing for, it falls back to the label (pc/mobiles/1: `content/events.ts` `genericEvent`). Screens and pcs can therefore change their keyword lists independently.

## Versions and isolation

- Each screen and pc version picks the protocol by import path: `@/components/transport/feed/1` and `@/socket/experiments/feed/1/protocol.mjs`. Any screen and pc on the same protocol version work together.
- A breaking change makes `feed/2`: copy both folders whole, change `version`, and register the new folder beside the old one in `socket/experiments/index.mjs`. Nothing is shared between protocol versions. The relay-side slots above were replaced in place on the day they were made, before anything else spoke feed/1.
- `components/transport/feed/<n>/` is the one sanctioned cross-experiment import in Goldfishes, as `desktop/native-windows/shared` is for desktop. Experiments still never import from each other.
- Event names come from `protocol.mjs` on both sides, so they are never copied by hand.
- Several screens: a pc follows the first screen whose snapshot reaches it, until that screen goes.
- Failure is isolated:
  - Offline, the screen's slots still step and nothing is sent, so the raft never waits on the relay; on rejoin the whole state goes out as a snapshot.
  - A pc applies pushes on a 16 ms timer, not `requestAnimationFrame`, which stops in a hidden or covered window.
  - The screen must stay visible (its own window, not a background tab): a hidden tab stops its frame loop, so the fish, and the feed, stop.
  - A pc without the relay can run `?source=demo`. This steps the same `slots.mjs` in the browser, fed by an imitation school, so its pushes have the screen's exact shape and timing.

## Log

- Browser console, prefix `[feed/1 screen]` / `[feed/1 pc]`, `?feedlog=0` silences it:
  - status changes and presence at once;
  - a summary every 2 s: contacts, detaches, departures, items and pushes on the screen; pushes, items, darkened slots and lit phones on the pc.
  - A screen whose page is hidden says so.
- Relay terminal, prefix `[goldfishes-feed:1]`: joins and leaves at once, and every 5 s while the room is not empty, the pushes and snapshots forwarded.
